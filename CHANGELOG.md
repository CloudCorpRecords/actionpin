# Changelog

## 0.1.7 (2026-10-23)

Fix release from Round 5 validation (Swarm C, C-5). 157 tests (138 prior plus 19 new in test/round5.test.ts), every new test failed against the published 0.1.6 code first except the two kept-behavior guards (a uses word inside a quoted run value, and a dynamic flow uses), which passed before and after.

- P-174 (BLOCKER): flow-style workflow uses entries were invisible. An audit of a workflow written in YAML flow style (jobs, steps, and uses all in flow mappings and sequences on shared lines) listed the file, inventoried zero actions, and verdicted PINNED, while the step used actions/checkout@v4 (mutable). Flow style is valid, GitHub-accepted YAML, and the README even listed it as a known limit; the limit is removed. A quote-aware flow scanner now inventories uses entries in flow mappings and sequences: several entries sharing one line, a flow step on a dash line, flow collections split across lines (tracked by flow depth), unquoted, single-quoted, and double-quoted values, quoted JSON-shaped keys, flow job-level reusable workflow calls, and flow anchors and aliases, all classified exactly like block-style entries. The repro repo now verdicts PARTIAL with the checkout@v4 ref classified MUTABLE. A uses word inside a quoted string, a run command, or a comment still invents no action, and block-style behavior is unchanged: cli/cli sparse .github at ed84a97a audits byte-identical on 0.1.6 and 0.1.7 (PINNED, 229 actions, all pinned).
- P-174 (verdict honesty): a workflow or composite file that carries a uses key whose value cannot be extracted no longer silently contributes zero actions to a PINNED verdict. The report names such files in a new unparsedWorkflows field, carries a note saying the file could not be fully parsed, and floors the verdict at PARTIAL; the pin plan inherits the note.
- P-174 (fix mode): pinning a flow entry no longer corrupts the line. The version comment is omitted on a flow line, where it would comment out the rest of the line, and when several flow entries share one line the plan chains the rewrite so applying it pins every entry on that line instead of overwriting one pin with the next.

## 0.1.6 (2026-10-22)

Fix release from the overnight flywheel chaos hunt (Swarm 4, hostile filesystem targets). 138 tests (122 prior plus 16 new in test/chaos.test.ts), every new test failed or hung against the published 0.1.5 code first, except the three kept-behavior locks (single .yml and .yaml file audits, and the P-014 empty-estate note), which passed before and after. One existing test was updated in place: the core test that asserted a nonexistent path returns PINNED without throwing now asserts the throw, because that leniency was P-078 itself.

- P-077 (REAL): a FIFO (named pipe) planted at .github/workflows/pipe.yml hung the audit forever, in 3 of 3 hunt runs and in the coordinator re-verification (killed by timeout). Discovery opened every name with a workflow extension, and opening a FIFO blocks until a writer appears. Discovery now checks stat type before any open: only regular files are returned as workflows, collected as composite action definitions, resolved as local action files, or read during an audit. A FIFO named action.yml under .github/actions, at the repo root, or behind a local uses path is skipped the same way, and a FIFO anywhere else in the tree is never opened. This matches the stat-before-open discipline injectcheck already had on the same tree.
- P-078 (REAL): `actionpin audit /nonexistent --json` returned verdict PINNED, total 0, exit 0, so CI wired to a mistyped path went green on nothing; hookcheck and injectcheck exit 2 on the same input. A nonexistent target is now a usage error: the audit throws, the CLI prints `error: Path does not exist: <path>` to stderr and exits 2 with no verdict, and the fix command and MCP tools surface the same error instead of a success report. A regular-file target keeps single-file audit only for .yml and .yaml files (the documented contract: passing an action.yml path directly parses it); any other regular file, such as a package.json, is a usage error exit 2 with a clear message instead of being treated as a workflow and verdicted PINNED over zero actions with no note. A target that is neither a file nor a directory (a FIFO, socket, or device) is a usage error too. A real but empty directory is unchanged: it still carries the P-014 empty-estate note and exits 0.

## 0.1.5 (2026-10-22)

Fix release from the overnight flywheel Wave D self-dogfood hunt (all three security tools run over the factory estate and each other). 122 tests (107 prior plus 15 new in test/waved.test.ts), every new test failed against the published 0.1.4 code first except the local-reference control probe, which passed before and after. Hunt report: ~/workspace/security-wave/overnight/waves/waveD/HUNT.md.

- P-067 (REAL, low): a root-level action.yml or action.yaml, the canonical location for a published GitHub Action, was only listed under unscannedComposites in a directory audit and none of its internal refs were inventoried. The proving case is CloudCorpRecords/greenlight: its guard workflow pins the shipped action by full SHA and the repo verdicted PINNED 10 of 10, while the root action.yml itself runs actions/setup-node@v4 internally, counted nowhere. A directory audit now scans the root-level action definition on the same terms as the P-058 composites, whether or not any workflow references it: its step uses refs are inventoried and classified like workflow steps, flagged as composite action refs in JSON and human output, covered by the pin plan, and drive the verdict the same way. JavaScript and Docker root actions (runs.using node or docker, no steps) count as scanned and add no refs. The scanned root file no longer appears in unscannedComposites; action files elsewhere in the repo that are still not scanned (not the root file, outside .github/actions, and unreferenced) are still named there. Self-reference cannot recurse or double count: the scan dedupes by resolved path, so a root action whose steps call the repo's own action via ./ or via its published name is scanned exactly once. Two tests that locked the old boundary were updated in place: the hardening battery scope test now asserts the root file is scanned, and the P-046 unscanned-remainder test now uses an unreferenced action file under tools/. The empty-estate note now fires only when neither workflows nor action definitions were found, so a repo whose only auditable surface is its root action definition is audited on it without a note claiming nothing was audited.

## 0.1.4 (2026-10-22)

Fix release from the overnight flywheel Wave B corpus expansion hunt (8 real repos, 975 refs, 99 hand-verified findings at 100 percent). 107 tests (93 prior plus 14 new in test/waveb.test.ts), every new test failed against the published 0.1.3 code first. Hunt report: ~/workspace/security-wave/overnight/waves/waveB-actionpin/HUNT.md.

- P-057 (REAL): a local action path with a stray prefix, `uses: $/.github/actions/issues-helper` as shipped 11 times by vitejs/vite, was classified MUTABLE third-party with an empty ref, single-handedly verdicted vite EXPOSED, and was sent to the GitHub API by fix, which parsed owner `$` and repo `.github` and emitted 11 FAIL lines. A uses value whose path is a .github/actions or .github/workflows path behind a malformed prefix is now classified LOCAL, is never resolved against the GitHub API, and still resolves to the composite on disk. The finding carries a note that the prefix is not a valid remote action reference and looks like a local path typo, so the upstream defect stays visible instead of being silently reclassified. On vite the shape is now 11 LOCAL refs with notes and the verdict is driven by the estate's real refs.
- P-058 (REAL, low): composite action internals inside the scanned repo were never audited in directory scans, so a mutable ref inside a local composite was invisible to the audit and the verdict (vite's .github/actions/issues-helper/action.yml holds 6 pinned actions/github-script refs that were counted nowhere). A directory audit now also scans every action.yml and action.yaml under .github/actions, plus any local action directory a workflow or a scanned composite references, following references without double-counting. Internal steps are inventoried and classified like workflow steps, flagged as composite action refs, and mutable refs inside a composite affect the verdict the same way workflow refs do. On vite the audit total rises from 44 to 50 with the composite's 6 pinned refs inventoried.
- P-046 (COSMETIC): the audit report carried no composite coverage statement. The report now lists the composite files scanned (a composites field in JSON and a count line in human output), and names any action files found elsewhere in the repo that were not scanned because they sit outside .github/actions and no workflow references them.
- P-059 (COSMETIC): the fix plan header counted only PIN entries while the body also listed ALREADY-PINNED lines, so header and body disagreed. The header now states both numbers plainly, in the form "N to pin, M already pinned", and the plan JSON carries an alreadyPinned count beside changes.

## 0.1.3 (2026-10-21)

Fix release from the overnight flywheel Wave A evasion hunt. No new features. 93 tests (72 prior plus 21 new in test/wavea.test.ts), every new test failed against the published 0.1.2 binary first. Hunt report: ~/workspace/security-wave/overnight/waves/waveA-actionpin/HUNT.md.

- Docker refs were classified PINNED on the shape of the string, not on validity: a truncated sha256 digest (sha256:abcd1234), a 64-character non-hex digest, and a mutable tag spelled as 40 hex characters (docker://myimage:<40 hex>) all counted as pinned, so a repo whose only container line carried an invalid digest verdicted PINNED with exit 0. A container image now counts as PINNED only with a full sha256 (64 hex) or sha512 (128 hex) content digest; every other docker ref is MUTABLE.
- YAML anchors and aliases (supported by GitHub Actions since September 2025) were mishandled three ways. A value anchor (uses: &name owner/repo@ref) was reported as a fabricated action named after the anchor token, and an alias (uses: *name) as a fabricated action named after the alias, so an anchored pinned action and its alias reported MUTABLE third-party instead of PINNED official. Anchors and aliases now resolve within the file: alias lines inherit the anchored classification and are flagged viaAlias in the report.
- A step anchor between the dash and the uses key (- &step uses: owner/repo@ref) made the line invisible: a workflow whose only step was written that way reported total 0 and PINNED. Step anchors in that position, anchors alone on the dash line, and step aliases (- *name) are now inventoried.
- Fix mode never rewrites an alias line: the plan marks it failed with an explanation that it is pinned when its anchor definition line is pinned, and pinning the definition line alone brings an anchored workflow to PINNED.
- Quoted uses values containing a space (a trailing space before the closing quote, or a comment inside the quotes) were cut at the space, leaving the action name with a stray leading quote and mislabeling official actions as third-party, which flipped PARTIAL verdicts to EXPOSED. The quoted scalar is now read to its closing quote.
- Version tags with an uppercase V (V4, V1.2.3) were classified BRANCH instead of MUTABLE because the version pattern only accepted a lowercase v. The pattern is now case-insensitive.

## 0.1.2 (2026-10-21)

Fix release from Round 1 real-repo validation. No new features.

- P-001 (REAL): piped output no longer truncates. The CLI called process.exit() immediately after printing, which cut stdout at exactly 65,536 bytes whenever a report was read through a pipe and still exited 0, handing agents and CI a corrupt JSON prefix with a success code. Six of the ten Round 1 corpus repos produced reports over that limit (the largest was about 696 KB). Every report now goes through an emit path that resolves only after stdout has flushed, and the exit code is applied with process.exitCode so the process ends naturally after delivery. If the reader closes the pipe early, the process exits 141 (128 + SIGPIPE) rather than reporting success for undelivered output. Regression tests pipe reports over 200 KiB through a real child process and parse them.
- P-014 (COSMETIC): an audit that finds no workflows now says so plainly. The report and plan carry a note stating that nothing was audited and the verdict covers an empty estate, instead of a bare PINNED with total 0 that read as an all-clear (the kubernetes/kubernetes case in Round 1).

## 0.1.1 (2026-10-21)

Hardening release. An adversarial battery of 31 cases (64 tests total, all passing) found and fixed five real bugs. No new features.

- Fix mode corrupted quoted uses values: the version comment landed inside the quotes (`uses: "actions/checkout@<sha> # v4"`). The comment now goes after the closing quote for both single and double quoted values, and the rewritten line round-trips through the parser.
- Fix mode silently stripped CRLF line endings from rewritten lines in Windows-style workflow files, leaving mixed endings. The original line ending is now preserved per line.
- Refs containing slashes (`release/v1`, `feature/new-thing`) could never be resolved: the ref was percent-encoded into the GitHub git-ref API path. Each ref segment is now encoded separately so slashes survive.
- Dynamic uses values (`${{ matrix.action }}`, `actions/checkout@${{ inputs.ref }}`) were reported as fabricated actions with nonsense refs. They are now skipped entirely and documented in the README limits, because they cannot be classified statically.
- `uses :` with a space before the colon (valid YAML) was not parsed at all. It now is.
- README gained a Limits section pinning the audited scope: workflow files only during directory audits (composite action.yml parses when passed directly), short SHAs never count as pinned, flow-style YAML is not detected, docker refs are reported but never rewritten.

## 0.1.0 (2026-10-21)

First release. Part of the security wave, the detection and hardening counterpart to Greenlight.

- `actionpin audit [path]`: scans .github/workflows for every uses: reference, classifies each as PINNED, MUTABLE, BRANCH, or LOCAL, labels official, third-party, docker, and local owners, and returns a PINNED, EXPOSED, or PARTIAL verdict with file and line evidence.
- `actionpin fix [path] [--dry-run]`: resolves mutable and branch refs to commit SHAs through the GitHub API and rewrites the uses: line in place to owner/repo@SHA with the original ref kept as a comment, preserving formatting line-wise. Local refs are never rewritten, and a failed resolution leaves the line unchanged.
- MCP server with `audit_workflows` and `pin_plan` tools. pin_plan returns the full fix plan without writing any files.
